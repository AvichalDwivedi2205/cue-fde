# Customer-to-engineering channel loop

Cue preserves the registered application and original customer conversation while an assigned engineer investigates an issue. Preview acceptance and production release are separate transitions.

## Current behavior

| Step | Binding and behavior |
| --- | --- |
| Native intake | Saved X/email configuration selects an active app. Event replays and thread references cannot cross app boundaries. Existing signed Slack threads retain their saved app. |
| Support draft | The stored app selects its name, published knowledge and current brand voice. Missing context requires manual review. |
| Engineering handoff | App routing names one connected engineer. A frozen issue/reproduction/policy context creates one Slack thread. Only its assigned member can start or decide that handoff. |
| Repair | The existing governed worker owns the run. Durable baseline, model and verifier records drive Slack updates. |
| Engineering approval | Slack decisions bind the thread, card, run and exact commit. Approval does not merge or deploy. Historical runs without handoffs retain their existing workflow. |
| Preview | The trusted deployment verifier registers the approved preview identity. A separate operator browser check records observations and updates widget conversations without resolving production. |
| Customer update | An immutable review binds exact text, sender, original destination, app, run and preview evidence. Explicit approval precedes an atomic send claim. Provider acceptance and independent read-back remain separate. |
| Email consent | Only the signed widget session can opt its conversation in or withdraw consent. Changed contact details invalidate prior email approval. Provider records do not establish inbox delivery. |
| Uncertain delivery | No blind retry. Same-target credential rotation permits verified read-only reconciliation, including while X sending is paused. |
| Quiet signals | Operators select saved native X cases or labelled manual input. Stable native author IDs prevent renamed handles inflating author counts. Product handoffs queue no implementation. |
| Public evidence | Existing synthetic v1 exports remain supported. Real-source v2 requires review of immutable input and analysis revision; exact unsafe text refuses export. Private identifiers and credentials stay out of public assets. |

## Operator setup

1. Choose the active registered app for each native channel in Setup.
2. Connect the intended X brand. Reply access requires a separate user-authorized token whose account matches the saved brand; app-only read credentials are insufficient.
3. Assign a connected Engineering or Owner member in Slack setup. An unassigned Owner has no implicit handoff override.
4. Save reproduction evidence and send the issue to its assigned engineer. Start the investigation from the resulting Slack thread.
5. Review the exact pending commit. Deploy its approved preview through the trusted verifier and record the original action and reload observations.
6. Prepare the customer update, review its exact destination and text, then approve sending. Reconcile uncertain outcomes through provider read-back.
7. Review selected signals before analysis and public export. Keep synthetic and native provenance explicit.

Use the user's own narration after picture lock. Do not claim production release, real customer traction or completed provider delivery from local tests or a preview receipt.
